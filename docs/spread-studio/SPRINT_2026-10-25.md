## Shared interface contracts (negotiate before implementation)

- `StudioAppearanceV1`: typed versioned JSON, generated and manually editable in React; mode `system|light|dark` separate from Studio appearance values; bounded color, material, typography, effects; user-selected photo referenced by opaque local asset ID.
- `StudioDraft`: proposed appearance + warnings, **no data writes**. Preview and Apply/Cancel distinguish draft from committed values.
- `AssetRef`: opaque ID, actual file bytes outside planner localStorage, orientation/size/format validated; meaningful error for missing image after backup/restore.
- `AIAvailability`: explicit states `available | unsupported | not-ready | error`, plus typed `proposeAppearance` request/response; available only for installed native iOS with the local `SystemLanguageModel`.
- `StudioIntent`: bounded instruction and target profile for foreground flow only, with truthful receipts and no automatic save.
- Do **not** reinterpret `data-theme` as the user's custom appearance; it remains light/dark/system. Theme changes must not touch `SpreadData`.

The first implementer to need a contract change should propose it on the relevant issue; do not independently invent incompatible types. Shared cross-cutting changes to `profiles.ts`, `store.ts`, `src/styles.css`, `ios/App/App.xcodeproj/project.pbxproj`, `package.json` and `AGENTS.project.md` require Claude/integration coordination to avoid overwrites.

## Integration order and gates

1. **Foundation gate**: G2 defines persistence/image lifecycle and G3 agrees token/appearance schema; G1 UI consumes it. Validate unsupported/missing assets and no planner mutation.
2. **Visual gate (50%)**: G1+G2+G3 integrated and actual Spread and Week screens shown with distinct user-customized appearances. Visual quality not just a color tint. Current design-system prohibition on new decorative styles must be explicitly amended and reviewed before acceptance.
3. **Local AI gate (75%)**: G4 Swift service emits constrained proposal that UI previews, with real-device offline/no-model fallback tests. Don't block the app on unavailable models.
4. **Siri gate (100%)**: G5 App Intents open Studio, deliver user request across cold starts, no success-before-persist; manual fallback and privacy review. Widgets and native task database are not minimum Studio acceptance conditions.
5. **Release gate**: Existing test suite, `npm run test:spread`, `npm run typecheck`, `npm run lint`, iOS build, backup/restore and accessibility coverage, manual iPhone/iPad QA, rollback and owner approval. Old baseline failures documented separately.

Never claim phase completion based only on code being written. Without signed physical-device evidence, on-device Foundation Models and Siri remain **unverified**, even if Swift compiles.
